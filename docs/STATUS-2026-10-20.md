## How to read this

There are two different claims a status report can make, and this codebase has
learned the hard way that they are not the same claim:

- **Shipped** — the code is written, it typechecks, it lints, and it is in the
  tree on `main`.
- **Proven** — somebody watched it do the thing, on real data, in a running app.

Most of what is "waiting" below is not missing code. It is missing *proof*.
Twenty-four of the 46 open items are live-verification tasks that were left
open deliberately, because the only way to close them is to sign in as staff and
operate the portal against the live database — and there is no staging database
to do it safely against. Anything written here as "verified" was verified by one
of the six gates listed in §6.

Every number in this report was re-derived from the working tree and the task
ledger on 2026-10-20. Nothing is quoted from memory or from an earlier report.

### 1.1 Every address the app serves

This is the whole surface, read out of the tree rather than out of a feature list.
Nothing here is aspirational: each line is a file that exists on `main`.

**Staff portal — `src/app/(admin)` (17 pages).** `(admin)` is a pathless group, so
the URL is the folder name with no prefix. Every one of these is a Server Component
that awaits `connection()`, calls `requireStaff("<own path>")`, and declares
`export const instant = false`.

| Address | What a recruiter does here |
| --- | --- |
| `/dashboard` | The live hiring overview: pipeline movement, AI fit scores, channel effectiveness across the group. |
| `/analytics` | Funnel behaviour over a 90-day window — open/finish rates, pool conversion, message delivery, panel load — and its export. |
| `/reports` | The row-level lists behind the analytics numbers (applications, issued tests, prospects, messages, interviews), downloadable as CSV/XLSX/PDF. |
| `/time` | The time ledger: hours logged against candidates, openings and hiring paperwork, plus export. |
| `/activity` | The change trail — who or what altered which record, when, through which door. Needs `settings.manage_platform`. |
| `/candidates` | Works the pipeline table: filter by stage/channel/company, open profiles, add by hand, browse the archive (`?archived=1`) or the ungraded queue (`?ungraded=1`). |
| `/candidates/[id]` | One person's whole dossier — every application, attempt, interview, file, message and stage change — keyed by the person, not the application row. The only nested page in the group. |
| `/sourcing` | The outbound prospect pool: people worked off-pipeline, outreach copy, convert-to-application. |
| `/jobs` | Browses and files openings across the group's companies (draft or published) and jumps to each role's applicant list. |
| `/questions` | The whole question bank in one place — unmarked apply-form questions and marked assessment questions — placed onto roles or suites. |
| `/assessments` | Builds Excel/video/case-study/quiz suites, issues candidate links, reads the answers those links returned. |
| `/interviews` | The day-grouped panel calendar: reslot, change interviewers, record the outcome. |
| `/onboarding` | New-hire onboarding: role-mapped checklists, skill-gap analysis, one plan per hire. |
| `/files` | Walks the private buckets folder by folder to see which record owns each file, opened through an expiring signed link. |
| `/whatsapp` | The messaging console: WhatsApp outbox buckets, what the email relay accepted, what sits in portal inboxes, with resend. |
| `/assistant` | Chats with the operations assistant to read or change records inside the caller's own permissions; reopens saved sessions (`?session=`). |
| `/settings` | One page serving many addresses through `?area=`/`?section=`/`?tab=`: settings values, master data, staff and roles, templates, provider credentials, model routing, the change trails. |

Seven of these are URL-state-driven — the page re-keys its child view off the query
string, so a drawer or a filter is a linkable address. That is what lets the
assistant, the alert cards and the chat deep-links land on a filtered page.

**Candidate portal — `src/app/(candidate)` (2 pages).**

| Address | What the candidate does here |
| --- | --- |
| `/portal` | Tracks their own applications by stage, reads the action-needed card and the notice inbox, starts or resumes an invited assessment, looks up by `?code=`. |
| `/test/[token]` | Sits the timed assessment itself — spreadsheet, case study, MCQ, video pitch — behind the unguessable issue token. |

Neither page calls a session helper. `/test/[token]` is authenticated by the token
alone, and `/portal` resolves the candidate from the code inside the tracker.

**Public — 5 pages.**

| Address | What it is |
| --- | --- |
| `/` | The brand landing page: hero, capability cards, subsidiaries. Points only at `/careers` and `/portal` — no staff route is advertised here (#96). |
| `/login` | Staff sign-in; carries the `?next=` return path the proxy wrote. |
| `/careers` | The filterable board plus the group/company story from master data, with the careers assistant beside it. |

| `/careers/apply/[id]` | The stepped application wizard: details (optionally prefilled from the CV), viability questions, CV upload, submit. |

**Route handlers — 21 files, 23 exported methods.** Grouped by who may call them:

| Handlers | Guard | What they do |
| --- | --- | --- |
| `/api/attempt/[token]` (GET), `/start`, `/draft` (PUT), `/submit`, `/video`, `/integrity` | The bearer token, checked against the row | The assessment runner's whole data plane: fetch the paper, start the clock, autosave answers, submit and grade, upload a video pitch (≤50 MB), append proctoring events. |
| `/api/careers/questions`, `/upload`, `/prefill`, `/about-me`, `/chat`, `/lead` | Anonymous — public form | Viability questions, CV storage, reading contact details out of a CV, drafting the About-you field, the careers chatbot, filing a chatbot lead into the sourcing pool. |
| `/api/files/link`, `/api/files/upload` | Session + `candidates.read` / `candidates.write` | A 15-minute signed link (forcing download for anything a browser could execute inline), and attaching a file to a candidate record with the row and the object written or rolled back together. |
| `/api/reports/export`, `/api/activity/export`, `/api/time/export` | Each re-checks its own permission, not the page's | The three download doors. Note that `/activity/export` checks `settings.manage_platform` and `/time/export` checks `time.track`, not the `analytics.export` they sit beside. |
| `/api/live` | Session | Holds the SSE connection that fingerprints the watched tables on the viewer's own session. |
| `/api/branding/logo` | Public | 302s to the wordmark set in Settings, so a branding change reaches every surface without a rebuild. |
| `/api/cron/grading`, `/api/cron/whatsapp` | `x-cron-secret` = `CRON_SECRET`, and 503 when unset | **The two routes nothing schedules.** See §2.4 — this is risk #1. |

**The edge gate.** `src/proxy.ts` is Next.js 16's rename of `middleware.ts` and
contains no logic of its own; it calls `updateSession(request)`. It matches
everything except static assets, so `/api/**`, `/careers/**`, `/portal` and
`/test/**` all pass through it — but only the 16 `STAFF_ROUTES` prefixes and
everything nested under them are *redirected*. Three ways, in order: no session →
`/login?next=…`; role outside `SUPER_ADMIN` / `RECRUITER` / `HIRING_MANAGER` →
`/portal?denied=staff-only`; idle past `security.session_timeout_minutes` (default
480) → `/login?next=…&reason=idle` with every `sb-` cookie and the last-active
cookie deleted. JWT revalidation is skipped for anonymous requests, because it only
runs when a non-empty `sb-*` cookie is in the jar. Public pages are never matched by
`isStaffPath`, so no redirect can fire for them — which is why each `/api/**`
handler self-guards. Timeout reads are memoised 60 s at the edge because `"use
cache"` is unavailable there.

No page and no route handler is dead: all 16 rail paths appear in both `NAV` and
`STAFF_ROUTES`, `/candidates/[id]` is linked from seven call sites, and every one of
the 21 handlers has a caller or a renderer in the repo.

### 1.2 The schema, table by table

`supabase/schema.sql` is the schema of record — it is regenerated *from the live

| **Assessments & grading** | `assessment_templates` (3), `assessment_questions` (2), `candidate_attempts` (2), `candidate_responses` (4), `integrity_events` (1) |

| **Master data** | `departments` (2), `locations` (2), `skills` (2), `role_families` (2), `role_family_skills` (2), `currencies` (2) |
| **Messaging** | `communication_logs` (2), `notification_templates` (2), `scheduled_whatsapp_jobs` (1) |
| **Sourcing** | `sourced_prospects` (2) |

**Where the trust actually sits.** All 94 policies admit an identity through three
doors, and the split matters for the migration (§5):

| Door | Policies | Mechanism |
| --- | --- | --- |
| Session identity | **80** | `auth.uid()` resolved into `user_profiles`, through `is_staff()` (66 uses), `has_permission()` (41), `is_super_admin()` (12), `current_user_profile_id()` (12), `user_tenant_id()` (11), plus 4 direct `auth.uid()` comparisons. |
| Attempt-token bearer | **5** | `current_setting('request.jwt.claims', true)::jsonb ->> 'attempt_token'` matched against `candidate_attempts.access_token`, or against the first storage folder name. |
| No identity at all | **9** | A literal `true` predicate — 5 `using (true)`, 4 `with check (true)`. |

Permission keys the policies actually reference: `settings.manage_platform` (23),
`candidates.write` (5), `time.track` (4), `settings.manage_users` (3),
`settings.manage_roles` (2), `jobs.manage` (2), `companies.manage` (2).

**Two tables have zero policies** — `provider_credentials` and
`credential_audit_log`. That is deliberate, not a hole: verified against the tree,
every read and write of both goes through `admin.from(...)`, the service-role client
that bypasses RLS (§2.1). A policy on them would change nothing.

**But "RLS enabled on 41 of 41" is not "RLS protecting 41 of 41."** The legacy pair
`public.jobs` and `public.applicants` has three policies each addressed `to public`
with a predicate of literally `true`, *and* a table-level grant of delete, insert,
update, truncate to `anon`. `public.tenants_and_companies` has a `tenants_read
using (true)` alongside its three scoped policies. Nothing in `src` references
`jobs` or `applicants` at all, and `schema.sql` seeds no rows into them — so they are
a writable, anonymously reachable surface on two tables the application does not use.
See risk #7.

**`rls_auto_enable()` is declared and never bound.** `schema.sql:1184` defines it as
an `event trigger` function, and it is granted EXECUTE to `anon`, `authenticated`,
`postgres`, `public` and `service_role` (lines 2077-2081). `grep -ci 'create event
trigger' supabase/schema.sql` returns **0** — the hook is not wired, so a new table
does *not* get RLS automatically. The comment on `currencies` (line 364) still
describes the promise as if it were in force. See risk #8.

**Load-bearing partial uniques** a reader would otherwise trip over:
`applications_one_live_per_job` (one live application per person per opening),
`time_entries_one_running_idx` (one running timer per person),
`sourced_prospects_linkedin_key`, `provider_credentials_provider_priority_key`,
`user_invites_pending_email_uniq`, `tenants_and_companies_one_group_profile`.

**The enum that is really two enums.** `app_role` carries six labels and `user_role`
four. `user_profiles.role` uses the four-label one while `roles.key` and
`user_invites.role` use the six, bridged by `::text` casts inside `has_role()` and
`has_permission()`. Two of the six roles (`SUBSIDIARY_HR_MANAGER`, `INTERVIEWER`) are
grantable in the `roles` table but **unreachable** through `user_profiles.role` —
that is why #334 and the staff-role question keep coming back.

**Reference rows are part of the schema file.** `schema.sql` seeds 235 rows across 13
tables — 9 companies plus 226 reference rows: `role_permissions` 54,
`role_family_skills` 28, `app_settings` 26, `skills` 22, `permissions` 20,
`notification_templates` 17 (13 WhatsApp, 4 email), `role_families` 14,
`currencies` 14, `departments` 13, `ai_model_config` 7, `roles` 6, `locations` 5,
`storage.buckets` 4. Business/demo data is separate (`supabase/seed.sql`, five
tables only). This is why the dump is the port artifact, not the migrations folder.

## 2. What is built — and how far the proof goes

### 2.1 Identity, tenancy and settings

Staff accounts, role-based access, and a per-company tenancy model. Settings are
stored as key/value rows in `app_settings` with a `NULLS NOT DISTINCT` unique
constraint on `(scope, company_id, key)`, which is what lets a single bulk write
carry mixed-scope rows. Provider credentials are encrypted **in the app**, not in
the database: `src/lib/crypto/secrets.ts` does AES-256-GCM envelope encryption
under a key derived from `SETTINGS_ENCRYPTION_KEY`, stores
`iv || ciphertext || authTag`, and is marked `server-only`, so importing it from a
Client Component is a build error — that is the guarantee that secrets never enter
the bundle. GCM authenticates as well as encrypts, so a tampered row fails to
decrypt rather than silently returning garbage credentials.

The idle staff sign-out is real, not decorative. `security.session_timeout_minutes`
is read in `src/lib/supabase/middleware.ts` and reached from `src/proxy.ts` —
Next.js 16 renamed the `middleware` file convention to `proxy`, so the edge gate
lives in that file now — and it was proven with a live session (#39). A failed
settings read is deliberately not memoised, so a database hiccup cannot pin the
shipped default for the next minute. `password_min_length` and
`link_validity_hours` are likewise enforced (#35),
as are `mask_scores_for_reviewers` (#111), `organisation.timezone` (#112) and
`organisation.locale` + `enabled_locales` (#113).

**Proven:** #15, #39, #116, #121, #290, #291. The staff-route guard is now
correct *by construction* — the directory tree, `STAFF_ROUTES`, and `NAV` are
held equal by a script that fails the build, which matters because seven of the
sixteen pages were previously rendering behind an in-page `requireStaff()` while
being invisible to the edge guard, silently opting themselves out of idle
sign-out.

**Waiting:** #334 (the role-permissions editor's gate does not match its own RLS
policy). #157 (the `analytics.export` permission description does not say what
it grants).

### 2.2 Hiring core: applications, screening, grading

Applications advance through stages via server actions; AI screening runs on
apply and can be triggered by hand; grading writes per-question AI rationale that
surfaces in the candidate drawer. Video pitches are transcribed and graded
(#25–#28). A recruiter can hand-score a response the AI parked for review (#225)
and retry AI grading from the console (#227). A rejection reason can be drafted
by AI (#314), and an offer letter is generated as a PDF and attached to the OFFER
stage email, then re-attached on an outbox retry (#365–#372).

Thresholds are enforced, not displayed: auto-advance and auto-reject (#41),
`bias_reduction` and `default_duration_minutes` (#42), autosave interval and
focus tracking (#37), feedback email/logo/toggle (#40), `interview_questions` (#114).

**Proven:** #15, #21, #83, #101, #138, #147, #156, #163, #168, #196, #203.

**Waiting:** #29 is the honest hole. Video-pitch grading is wired, and typecheck
and lint passed, but **a real recorded pitch has never been graded end to end**.
Producing the fixture needs a manufactured `.webm` (Windows TTS + a browser
re-mux), and the candidate buckets reject WAV, so it is not a quick task.
#226, #229 and #232 need a signed-in session. #212 (read an attached CV into the
record so screening can run) is in progress.

### 2.3 Messaging: WhatsApp, email, in-app

Three channels, one outbox. WhatsApp dispatch goes through a queue with
retry/cancel (#18, #48). Notification templates are wired into the WhatsApp
sender (#34) and the console has reset-to-default and delete (#140–#141). The
schema of record seeds 17 templates — 13 WhatsApp, 4 email. SMTP transport was
added (#56) and is wired to stage changes and interview notices (#57), recruiter
bulk campaigns (#58), and an email + in-app panel with retry in the admin outbox
(#60). Candidates get an in-app notification centre (#59).

This area contains the most deliberate honesty work in the project. Portal
notices are no longer counted as deliveries (#217), the candidate dossier no
longer describes a portal notice as a delivery (#218), campaign sends are written
to the record and the inbox (#215), and an email re-send now renders what the
candidate would actually receive (#216).

**Waiting, and this is the important one:** #62. There are real SMTP
credentials in `.env.local` now, and rows log `delivered=true`, so a failed row
is a genuine bug rather than a placeholder artifact — but **one clean
delivered-message proof has not been recorded**. The WhatsApp side is bounded by
the Meta test account: notices enqueue correctly, delivery is rejected by Meta
(expired token / allow-list), and no scheduler drains the queue, so the queue
must be inspected at `/whatsapp` rather than by waiting for the phone.

### 2.4 Nothing schedules the cron routes

`src/app/api/cron/` contains exactly two route handlers: `grading` and
`whatsapp`. Both exist. **Neither is scheduled.** The grading sweep that
re-grades stuck `SUBMITTED` attempts (#23) and the WhatsApp queue drain (#18)
only run when something calls those URLs. This is why the queue appears to
stall: it is not stalled, it is unscheduled. That fact also shapes the platform
migration (§5) — a self-hosted container gives us a scheduler, which is one of
the few places where leaving the old platform makes the product *better*.

### 2.5 Sourcing and profiles

`linkedin_sourced_prospects` with outreach logging (#63), an import parser (#64),
convert-to-application (#65), a board and drawer UI (#66). Profile reading works

**Waiting:** LinkedIn reads stay credential-free by design — no login
automation. Two of the three doors (pasted text, save-to-PDF) are implemented.

### 2.7 The assistant

**Waiting:** #256, #267, #274, #278, #350, #352, #243 — all session-gated.

## 4. Risks that are live today

1. **Nothing drains the queues.** `grading` and `whatsapp` cron routes have no
   scheduler. `SUBMITTED` attempts can sit ungraded and WhatsApp notices can sit
   queued indefinitely, silently.
2. **Email delivery is unproven on real credentials.** Rows say
   `delivered=true`; one clean proof has not been recorded (#62).
3. **Video-pitch grading has never run end to end on a real recording** (#29).
4. **#334** — the role-permissions editor's gate does not match its RLS policy.
   RLS is 94 policies over 41 tables; a divergence there is a permission
   boundary, not a UI defect.
5. **Migrations drift from the live schema.** 28 authored files ≠ applied state.
   `supabase/schema.sql` is regenerated *from live*, including the console's
   reference rows, precisely because the file set cannot be trusted as the
   current truth. Any change to schema must be diffed against live, not against
   the migrations directory.
6. **AI providers are on free tiers.** OpenRouter returns daily 429s and Google
   flaps per-model 503s. A failure in the grading or screening path is more
   likely to be a provider quota than a code bug; retry before debugging.
7. **Two tables the app does not use are writable by an anonymous visitor.**
   `public.jobs` and `public.applicants` carry three policies each addressed
   `to public` with a predicate of literally `true`, and `schema.sql:1915-1918`
   and `:2039-2042` grant them delete, insert, update and truncate to `anon`.
   Nothing in `src` references either table and neither is seeded, so the blast
   radius is two empty legacy tables — but "RLS enabled on 41 of 41" is not the
   same statement as "RLS protecting 41 of 41", and nine policies do not
   constrain anything. Worth closing while the schema is being ported anyway.
8. **`rls_auto_enable()` is declared, granted, and never bound.** The function
   exists at `supabase/schema.sql:1184` and is granted EXECUTE to `anon`,
   `authenticated`, `postgres`, `public` and `service_role` (2077-2081), but the
   file contains **no `CREATE EVENT TRIGGER`** — so nothing wires it, and a new
   table does *not* get RLS automatically. The column comment on `currencies`
   (line 364) still asserts the promise as if it were in force. Every new table
   must enable RLS explicitly.

And the meta-risk this report exists to name: **the gap between shipped and
proven is now 21 sessions wide**, and every one of them is cheap individually.

## 5. The platform migration

Driving work. The owner is leaving Supabase and Vercel entirely for Docker-based
self-hosting. Eight decisions are locked, all taken deliberately:

1. **Own the whole stack** — sovereignty and lock-in removal, not cost.
2. **A rented VPS with Docker Compose.**
3. **Carry everything over** via one `pg_dump`, with encryption at rest.
4. **Port the RLS model with a shim** — stand-in `auth` and `storage` schemas,
   the data layer sets `request.jwt.claims`, so all 94 policies stay untouched.
5. **Hand-roll sessions** over the migrated bcrypt hashes, with an own sessions
   table.
6. **Self-host PostgREST** so the query code does not change.
7. **`/data/uploads` on a volume** plus a `files` table we own.
8. **One planned freeze.**

The measured coupling that these decisions are sized against, from the tree today.
Note the care taken here, because an earlier draft of this report got it wrong: a
plain `grep '.from('` returns **499** lines, but 29 of those are `Buffer.from`,
`Array.from` and `Object.from`, and 26 more pass a variable rather than a table
name. The number that actually sizes the PostgREST decision is:

| Coupling | Count |
| --- | --- |
| `.from("table")` reads against PostgREST | **444**, across 65 files |
| `.from(variable)` bucket/table references | 26 |
| `supabase.storage.from(bucket)` | 5 (a subset of the above) |
| `supabase.auth.*` call sites | 19 |
| Files importing `@supabase/*` | 13 |

Keeping the PostgREST query layer is what makes ~470 query call sites survivable;
rewriting them is not a migration, it is a rebuild. The 13 importing files and the
19 auth call sites are the parts that genuinely have to be hand-written.

The env surface still named for the old platform — `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`,
`SUPABASE_DB_PASSWORD` — is a rename and re-point job, not a redesign.

Two findings from this report's verification pass, both good news for the dump:

- **Encryption at rest survives the move untouched.** Credentials are sealed
  app-side with AES-256-GCM (`src/lib/crypto/secrets.ts`), not by the database, so
  a `pg_dump` carries opaque ciphertext that only Node + `SETTINGS_ENCRYPTION_KEY`
  can open. Nothing to re-wrap, and the key never has to enter the database.
- **`supabase_vault` is declared and unused, and it will break the restore.**
  `supabase/schema.sql:27-32` declares four extensions into an `extensions`
  schema — `pg_stat_statements`, `pgcrypto`, `uuid-ossp` — plus
  `create schema vault` with `supabase_vault`. The first three exist in plain
  Postgres (`pg_stat_statements` needs `shared_preload_libraries`;
  `gen_random_uuid()` is core from PG13 anyway). **`supabase_vault` does not.**
  Nothing in `src` references it and no migration uses it, so those two lines are
  platform residue that a vanilla restore will fail on. Drop them as part of
  decision 4's shim work.

**What has to change before the dump will restore on plain Postgres.** Every line
number below was read out of `supabase/schema.sql` today, not remembered. This is the
honest size of decision 4's shim work — the file's own header already warns that it
does not apply on vanilla Postgres, and here is precisely why:

| Blocker | Lines | What to do about it |
| --- | --- | --- |
| `create schema vault` + `supabase_vault` | 30-31 | **Delete.** No PostgreSQL distribution has that extension; `if not exists` does not save you when the control file is absent. Nothing in `src` references `vault` and no migration uses it — pure platform residue. |
| `pg_stat_statements` | 28 | Errors unless `shared_preload_libraries` is set in the container's `postgresql.conf`. Set it, or drop the line. |
| The `auth` schema | 987 and 9 call sites inside functions/policies | `user_profiles.auth_user_id` FKs to `auth.users(id)`, and `auth.uid()` is called from 80 policies. Stand in an `auth` schema (a stub already exists at `scripts/local-supabase-stub.sql`) and make `auth.uid()` read a GUC. |
| The `storage` schema | Policies 1789-1827, grants 2148-2183 | Eight policies are authored *on* `storage.objects`, plus `storage.foldername(name)` (granted to `PUBLIC` at 2183) and `insert into storage.buckets` at 2189-2208. This is decision 7's `files` table replacing them. |
| The database roles | 1903 onward | `anon`, `authenticated`, `service_role` and `postgres` must be created before any grant parses. PostgREST needs the `anon`/`authenticated` roles to exist as JWT-mapped logins. |
| **The `maintain` privilege** | Every table grant, 1903-2183 | `grant delete, insert, **maintain**, references, select, trigger, truncate, update …` — `maintain` is **PostgreSQL 17+ only**. On 16 or below this is a syntax error on hundreds of lines. Pin the container to PG17+, or regenerate the grants. |
| `UNIQUE NULLS NOT DISTINCT` | 696 | PostgreSQL 15+. Pins the floor on the version either way. |
| `alter publication supabase_realtime add table …` | 2217, 2223 | Wrapped in `exception when undefined_object`, so it degrades quietly rather than failing. Only `applications` and `candidate_attempts` are in the publication — and nothing in the app uses Supabase Realtime; the live channel is `/api/live` SSE plus polling. Drop both lines. |
| Sequence granted to `anon` | 1926-1929 | Legal anywhere, but `anon` can burn `nextval('application_tracking_seq')`. Combined with `applications_public_insert … with check (true)` that is the widest write path in the schema — the public apply form. Keep it deliberately, not by accident. |
| `request.jwt.claims` reads | 5 policies | **The silent one.** Legal syntax on vanilla Postgres, returns NULL if the GUC is never set — so the whole attempt-token door admits nobody and assessment links break with *no error at all*. This is why the identity port must be proven against a PostgREST we own, not against the current host. |

`APP_URL` already exists and defaults to `http://localhost:3001`, so links are
host-agnostic (#313) — that half is done.

**State: still in the brainstorming gate.** #373 (clarify constraints) is closed.
#374 is open because the choice between the three proposed approaches has not
been made. No migration code exists, and none should until an approach is picked
and a design is approved. One upside worth noting: a container gives the cron
routes the scheduler they have never had (§2.4), so this migration fixes risk #1
as a side effect.

Three of those commands are anchored on purpose, because an unanchored version of
each produced a wrong number in an earlier draft of this report:

- `grep -ci 'create table' supabase/schema.sql` returns **42**, not 41. The extra hit
  is inside the body of `rls_auto_enable()` at line 1197, where the function's own SQL
  string contains the words. Anchor on `^create table if not exists public\.` or you
  report a table that does not exist.
- The same trap on the RLS line: unanchored `grep -c 'enable row level'` also returns
  **42**, because `rls_auto_enable()` contains that statement too. Anchored, it is 41.
- `.from(` the same way: **499** raw hits is a real grep and a false metric (see §5).

The task totals are counted from the live task ledger, not from the previous turn's
summary — the ledger had drifted by one closed task between drafts.

The verification gates this project uses, in the order they are run:

1. `tsc --noEmit -p tsconfig.json`
2. `eslint` on the changed files
3. `node scripts/check-staff-routes.mjs` — tree / guard / nav must agree
4. `node scripts/check-themes.mjs`
5. An isolated production build in a hard-linked copy — the only proof that a
   `"use server"` file exports async-only things, run without touching the
   dev server on port 3001
6. A plain-Node live probe against the real database, which reads what it wrote
   and then undoes it

**What this report cannot claim.** Gates 1–6 prove code correctness and
type-level consistency. They do not prove a page renders, a drawer opens, an
email lands in an inbox, or a chart is legible. Where this report says "Proven"
it means a browser session or a live read observed the behaviour. Where a claim
rests on geometry audit or save-and-reopen only, that is stated. No visual
review of the companion deck was performed, and no unproven path in this
document has been upgraded to "done" to make the totals look better.
